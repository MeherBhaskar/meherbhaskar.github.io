Here is a test I run on every agent system before it ships: it is 2am, the agent is doing something wrong in production, and my phone buzzes. Three questions. Who is being woken up? What can they do about it? How fast can they stop the bleeding?

Most systems fail all three. Nobody is woken up because there are no alerts. Nobody can do anything because there is no kill switch, no rollback, no lever of any kind. And stopping the bleeding means finding the engineer who wrote the prompt six months ago and hoping they are awake.

Operational ownership is a design input, not an afterthought. If you cannot answer the 2am questions, you are not ready to launch.

## The kill switch

Every agent system needs a kill switch: a single action that stops the agent from acting, immediately, without deploying code, without a meeting, without the original author. What exactly it stops depends on the system: halt all runs, disable a specific tool, freeze outputs pending review, revert to a safe static mode. Define it per system, but define it.

Three properties make a kill switch real. First, it is fast: seconds, not the twenty minutes a deploy takes. Second, it is accessible to whoever is on call, not just the team that built the thing. Third, it has been tested. A kill switch that has never been pulled is a theory. Pull it in staging. Pull it in a game day. Know that it works before the night you need it.

The common objection is that kill switches are for dangerous systems, and ours just answers questions. But "just answers questions" is doing a lot of work in that sentence when the questions involve money, medical information, legal advice, or anything a user will act on. And even for harmless systems, a runaway agent burning budget or spamming users at 2am is an incident. The kill switch is not about danger. It is about control.

## Alert on the right signals

Most alerting I see is either absent or useless: alerts on raw error counts that fire constantly and get ignored, or no alerts at all because "we will notice." You will not notice. At 2am, nobody notices.

Alert on signals that mean something is wrong with the product, not the infrastructure. Task success rate dropping below its baseline. Cost per task spiking. Tool failure rate crossing a threshold. User correction rate climbing. These are the vital signs of an agent system, and they move before users complain.

Two disciplines keep alerts useful. First, every alert needs an owner and a runbook entry: who responds, what they check first, what the kill switch does. An alert without a runbook is just a notification that something is wrong somewhere, which is another way of saying it is noise. Second, review your alerts the way you review code. Alerts that never fire are untested. Alerts that fire constantly are broken. Both need fixing, and the fixing happens during the day, not at 2am.

## Runbooks for agent-specific failures

A runbook that says "restart the service" was written for a different era. Agent failures need agent-specific playbooks: the model is producing confident wrong answers (check the retrieval layer, check for prompt drift, consider stepping down the fallback ladder), a tool is returning corrupt data (disable the tool, fall back to cached or heuristic mode), the agent is looping (kill the run, check the retry guards, review the trace), outputs suddenly got worse after a deploy (roll back the prompt version, run the eval set against both versions).

Write these before launch, when you are calm and the failure modes are hypothetical. During the incident, nobody is writing documentation. They are following it or improvising, and improvisation at 2am is how small incidents become large ones.

The runbook also needs the map: where are the traces, where are the evals, where is the kill switch, who owns each piece. An incident responder who has to discover the system's anatomy during the incident is already losing.

## Incident reviews that feed the eval set

After the incident, do the review, and make it count twice. First, the usual: what happened, why, what we are changing. Second, the agent-specific step: every failure becomes eval cases. The exact inputs that produced the bad behavior go into the golden set, labeled, so the regression suite now covers the thing that bit you.

This is how reliability compounds. Each incident makes the eval set stronger, which makes the next incident less likely, which is the opposite of the usual pattern where incidents are survived and then forgotten. Teams that do this get steadily more reliable. Teams that do not get steadily more incidents.

Be honest in the review about ownership gaps. If the answer to "who owns this" was unclear during the incident, that is a finding, not an embarrassment. Fix the ownership, not just the bug.

## Run the 2am test as a game day

Reading this post is not the same as being ready. The way to close the gap is a game day: a scheduled, controlled incident where you deliberately break the agent and practice the response. Kill the model endpoint. Corrupt a tool's responses. Flood the system with adversarial inputs. Then watch what happens.

The first game day is always humbling. The kill switch takes four minutes instead of four seconds because nobody remembers where it is. The runbook references a dashboard that was renamed. The alert fires, but to a channel nobody watches anymore. The on-call engineer, this is you, discovers all of this at 2pm on a Tuesday instead of 2am on a Saturday, which is the entire point.

Do this quarterly. Rotate who plays the on-call role, because the test is only valid if the responder did not write the system. Each game day produces findings, and the findings go into the runbook, the eval set, and the alert configuration. Over a year, this practice does more for reliability than any architecture change, because it tests the whole socio-technical system: the code, the tooling, the docs, and the humans.

The teams that skip game days always have the same reason: we are too busy shipping. They are busy shipping the system that will page them at 2am with no runbook. The game day is not time away from real work. It is the rehearsal that makes the real work survivable.

## "The team owns it" means nobody owns it

The deepest failure mode is diffuse ownership. The agent was built by a team, the team collectively owns it, and therefore at 2am everyone assumes someone else is handling it. Collective ownership of operations is no ownership.

Name a human. For every agent system in production, there is a named owner who is accountable for its behavior, who gets the page, who runs the incident review, who keeps the runbook current. The owner can rotate. The owner can delegate. But at any given moment, the name exists and everyone knows it.

This feels bureaucratic until the first incident, at which point it feels like the most obvious thing in the world. The 2am test does not ask for a committee. It asks for a name, a lever, and a plan. Who gets woken up. What they can do. How fast they can stop it.

Run the test on your systems this week. If you cannot answer all three questions, you have your roadmap. And it is not a feature roadmap. It is an ownership roadmap, which is the one that matters at 2am.

Can you name the owner of every agent you have in production right now?
